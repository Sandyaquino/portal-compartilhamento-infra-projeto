Tabela nova para a tela "Contratos" (gestão do contrato / solicitação de ação
a times de Técnico, Negociação e Comercial).

Você NÃO precisa rodar isso manualmente: o endpoint (routers/provedores.py,
função _solicitacoes_garantir_tabela) já tenta criar a tabela sozinho na
primeira vez que for chamado, do mesmo jeito que TB_ACAO (mapa de postes) e a
tabela de OTP do login já funcionam hoje nesse projeto. Este .txt existe só
como referência/documentação do schema, e pra você poder rodar manualmente
via HANA Studio/DBeaver se preferir validar antes de bater nos endpoints.

Ajuste o schema "CLB349328" abaixo se o schema de trabalho for outro.

--------------------------------------------------------------------------
CREATE COLUMN TABLE "CLB349328"."PORTAL_COMPARTILHAMENTO_SOLICITACAO_ACAO"
(
    "ID_SOLICITACAO"        INTEGER CS_INT GENERATED BY DEFAULT AS IDENTITY,
    "ID_PROVEDOR"           INTEGER NOT NULL,
    "ID_PROCESSO"           INTEGER,
    "ID_ACAO_POSTE"         INTEGER,
    "TIPO_ACAO"             NVARCHAR(30) NOT NULL,
    "TIME_RESPONSAVEL"      NVARCHAR(20) NOT NULL,
    "DESCRICAO"             NVARCHAR(2000),
    "PRIORIDADE"            NVARCHAR(10) DEFAULT 'MEDIA',
    "STATUS"                NVARCHAR(20) DEFAULT 'ABERTA',
    "SOLICITADO_POR"        NVARCHAR(100),
    "DATA_SOLICITACAO"      LONGDATE CS_LONGDATE,
    "RESPONSAVEL_EXECUCAO"  NVARCHAR(100),
    "DATA_CONCLUSAO"        LONGDATE CS_LONGDATE,
    "OBSERVACAO_CONCLUSAO"  NVARCHAR(2000),
    "CREATED_AT"            LONGDATE CS_LONGDATE,
    "UPDATED_AT"            LONGDATE CS_LONGDATE,
    PRIMARY KEY ("ID_SOLICITACAO")
)
UNLOAD PRIORITY 5 AUTO MERGE;
--------------------------------------------------------------------------

Domínio de valores usado pelo backend (validado em código, não por
constraint de banco — mesmo padrão do resto do projeto):

TIPO_ACAO x TIME_RESPONSAVEL (catálogo fixo em routers/provedores.py,
constante CATALOGO_TIPOS_ACAO — adicione novos tipos ali, não é preciso
alterar a tabela):
  REMOCAO            -> TECNICO     ("Solicitar remoção")
  NOTIFICACAO        -> COMERCIAL   ("Encaminhar notificação ao provedor")
  COBRANCA           -> NEGOCIACAO  ("Solicitar cobrança")
  DESFAZER_CONTRATO  -> COMERCIAL   ("Solicitar desfazimento do contrato")
  OUTRO              -> COMERCIAL   ("Outra solicitação")

STATUS: ABERTA | EM_ANDAMENTO | CONCLUIDA | CANCELADA
PRIORIDADE: BAIXA | MEDIA | ALTA

ID_ACAO_POSTE (novo): quando a solicitação é do tipo REMOCAO e o usuário
seleciona postes/ocupações do provedor, o backend também grava uma ação de
verdade em PORTAL_COMPARTILHAMENTO_ACAO_POSTE (a mesma tabela do Mapa de
Postes) e guarda o ID gerado aqui - assim o time técnico vê a mesma ação
nos dois lugares, em vez de duas coisas desconectadas. Isso também exigiu
adicionar "REMOCAO" ao conjunto de tipos válidos de TIPOS_ACAO_VALIDOS em
routers/postes.py (antes só FISCALIZACAO/ORDENAMENTO) - não muda o schema
de PORTAL_COMPARTILHAMENTO_ACAO_POSTE, só o valor aceito na coluna TIPO.

Nenhuma outra tabela nova é necessária — a lista de "provedores que
percorreram toda a jornada" (tela Contratos) e a timeline do provedor
reaproveitam PORTAL_COMPARTILHAMENTO_PROVEDOR, _PROCESSO, _JORNADA,
_ENTRADA, _HISTORICO_ENTRADA e _CONTATO_PROCESSO, que já existem. O vínculo
com o Mapa de Postes usa PORTAL_COMPARTILHAMENTO_OPERADORA e
_POSTE_OCUPACAO, ligando por CNPJ com PORTAL_COMPARTILHAMENTO_PROVEDOR
(tabelas independentes historicamente, sem FK entre elas).
